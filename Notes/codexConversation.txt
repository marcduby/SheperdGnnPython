Yes. The repo’s rebuild path for those two files is:

1. Build the KG shortest-path matrix
2. Derive the patient-level SPL artifacts from it

The exact scripts are:

- `data_prep/shortest_paths/shortest_paths.py`
- `data_prep/shortest_paths/add_spl_to_patients.py`

What each one does:

- `shortest_paths.py`
  - Reads the KG
  - Computes all-pairs shortest paths
  - Writes `KG_shortest_path_matrix_onlyphenotypes.npy` in `project_config.KG_DIR`

- `add_spl_to_patients.py`
  - Reads your patient JSONL files
  - Reads `KG_shortest_path_matrix_onlyphenotypes.npy`
  - Aggregates phenotype-to-gene shortest path values per patient
  - Writes:
    - `*_spl_matrix.npy`
    - `*_spl_index_dict.pkl`

The output naming is defined directly in `data_prep/shortest_paths/add_spl_to_patients.py`:

- Matrix:
  - `project_config.MY_DATA_DIR / f'{args.save_prefix}_agg={args.agg_type}_spl_matrix.npy'`

- Index dict:
  - `project_config.MY_DATA_DIR / f'{args.save_prefix}_spl_index_dict.pkl'`

› why are all these pkl files needed if they can be generated from the graph in real time


• Because the repo is written to consume a preprocessed KG, not to rebuild all derived structures at runtime.

  There are two different reasons.

  First, some .pkl files are not just “graph caches”; they are semantic lookup tables the raw edge list does not fully provide. Examples:

  - hpo_to_idx_dict_*.pkl
  - ensembl_to_idx_dict_*.pkl
  - mondo_to_idx_dict_*.pkl
  - orphanet_to_mondo_dict.pkl

  These let the patient loader turn external identifiers from your JSONL files into the exact node indices used by the KG. The model needs that alignment to be stable and identical across runs. In
  this codebase, shepherd/dataset.py loads those directly instead of reconstructing them every time.

  Second, some files are expensive derived features that would be slow to recompute online:

  - degree_dict_*.pkl
  - *_spl_matrix.npy
  - *_spl_index_dict.pkl

  The SPL files are the main example. They encode shortest-path-derived features used by train.py and predict.py. Recomputing shortest paths from each patient phenotype set to candidate genes
  during training would be much slower and would complicate batching a lot. Precomputing them makes training deterministic and tractable.

  So the short answer is:

  - some .pkl files hold identifier mappings and ontology mappings that the model needs in exact preprocessed form
  - others are performance-oriented cached graph features
  - the repo chose offline preprocessing for reproducibility and speed, not on-the-fly graph derivation

  Could they be generated at runtime? In principle, yes for some of them.
  But in this repo:

  - the code does not implement that path
  - doing it online would slow training/prediction
  - it would also make data preparation less explicit and easier to get wrong

  If you want, I can separate the required files into:

  1. “can be rebuilt cheaply from KG_node_map.txt”
  2. “need external ontology/data mappings”
  3. “expensive precomputed features”

• This repo is a research codebase for SHEPHERD, a rare-disease diagnosis system built on a knowledge graph plus patient phenotype data. At a high level, it does three things: rank candidate
  genes, find similar patients, and rank likely diseases. The center of the repo is the shepherd/ package; data_prep/ is for building or adapting datasets; project_config.py is the global path/
  config switchboard.
  The runtime flow is:
  1. project_config.py defines where the knowledge graph, patients, checkpoints, and results live: project_config.py
  2. Graph data is loaded from TSV files into a PyG Data object by preprocess_graph(): shepherd/preprocess.py
  3. Patient JSONL files are loaded and converted from HPO / Ensembl / MONDO identifiers into KG node indices by PatientDataset: shepherd/dataset.py
  4. A GATv2-based node encoder produces embeddings for graph nodes: shepherd/node_embedder_model.py
  5. A task head consumes phenotype embeddings plus candidate genes, diseases, or other patients:
      - Gene ranking uses GPAligner: shepherd/task_heads/gp_aligner.py
      - Patient/disease retrieval uses PatientNCA: shepherd/task_heads/patient_nca.py
  6. Training is orchestrated in train.py; prediction-only runs are in predict.py: shepherd/train.py, shepherd/predict.py
  The model architecture is layered:
  - NodeEmbeder learns graph node embeddings with 3 GATv2Conv layers and a relation-aware link-prediction decoder. That is the KG pretraining / auxiliary objective: shepherd/
    node_embedder_model.py
  - CombinedGPAligner wraps the node encoder plus a phenotype-to-gene aligner for causal gene discovery: shepherd/gene_prioritization_model.py
  - CombinedPatientNCA wraps the same node encoder plus an NCA-style retrieval head for patient-patient or patient-disease similarity: shepherd/patient_nca_model.py
  The three supported tasks are selected by --run_type, and that switch mainly changes loss/head selection inside get_run_type_args():
  - causal_gene_discovery -> aligner model + multi-similarity loss
  - patients_like_me -> patient_NCA + patient-patient NCA loss
  - disease_characterization -> patient_NCA + patient-disease NCA loss
    See: shepherd/hparams.py
  Data expectations are strict. Each patient is one JSON object per line, usually with:
  - id
  - positive_phenotypes as HPO IDs
  - all_candidate_genes as Ensembl IDs for gene ranking
  - optional true_genes
  - optional true_diseases
    See: data_prep/README.md, project_utils.py
  One important implementation detail is that this repo depends on a lot of precomputed artifacts outside Git:
  - KG node/edge TSVs
  - HPO / Ensembl / MONDO lookup pickles
  - shortest-path matrices for patients
  - pretrained checkpoints
  That’s why project_config.py and the shortest-path prep docs matter so much: data_prep/shortest_paths/README.md

  - rows: patients
  - columns: genes
  - value: aggregated score of each candidate gene against that patient’s phenotype set
  A good aggregation is something like:
  - sum of log probabilities across observed phenotypes
  - mean of log probabilities
  - noisy-OR style aggregation
  - any calibrated score where higher means “this gene better explains this patient’s phenotype set”
  So the format I recommend is:
  - patients/<dataset_name>_gene_phen_prob_matrix.npy
      - shape: (n_patients, n_genes)
      - dtype: float32
      - each row corresponds to one patient
      - each column corresponds to one KG gene node
  - patients/<dataset_name>_gene_phen_prob_index_dict.pkl
      - maps patient ID to row index
  - optionally, the upstream raw table:
      - columns: gene_id, phenotype_id, probability
  The gene column order should match the KG gene node order already used here:
  - the code builds that ordering from KG node-map gene nodes in shepherd/predict.py:113
  Where to put it:
  - under PROJECT_DIR / 'patients'
  - alongside the existing SPL artifacts referenced from project_config.py
  Why this is the right place:
  - training already knows how to load a per-patient, per-gene numeric prior from disk in the sampler: shepherd/samplers.py:438
  - scoring already mixes that prior with learned phenotype-gene similarity in the aligner: shepherd/task_heads/gp_aligner.py:108
  So the clean implementation is:
  1. Add new config paths in project_config.py
  2. Load your matrix in train.py/predict.py or directly in the sampler
  3. Slice it per patient/candidate gene exactly like batch_cand_gene_to_phenotypes_spl
  4. Blend it into _calc_similarity() as another prior term
  Conceptually, your score per candidate gene should become something like:
  final_score = a * learned_embedding_score + b * spl_prior + c * gene_phen_prob_prior
  with a + b + c = 1 or with separate learned weights.
  One important modeling point: because your data comes from thousands of sequenced patients, it is a population prior. That makes it excellent as a scoring prior, but risky as a KG edge
  replacement. Keeping it separate lets you:
  - preserve the quantitative value
  - tune its contribution
  - ablate it cleanly
  - avoid contaminating the KG topology with confidence-weighted edges the encoder cannot represent
